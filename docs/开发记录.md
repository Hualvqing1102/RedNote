## 阶段 9 · 桌面版"打开无响应"问题排查与修复（09-06）

**现象**：RedNote 从单文件 exe 改为**文件夹版(onedir)**后，双击打开窗口"无法响应"（能出窗但拖不动、点不了）。

**排查过程**
1. 复现：启动 `dist\RedNote\RedNote.exe`，本地服务其实已起来（`/api/notes` 200），但进程 `Responding=False` → UI 主线程被卡。
2. 排除法：
   - 用最小 pywebview 探针分别打 onedir 控制台 / windowed / 本地 http 导航 → **全部正常**，说明基础壳与打包形态没问题；
   - 把真实应用打成控制台版 → 同样卡死；而源码直接 `python run_desktop.py` → 正常 → 是"真实应用 + 冻结打包"的组合差异；
   - 安装 py-spy 抓冻结进程线程栈：主线程停在 `winforms.py create_window`，后台线程卡在 `webview/util.py get_functions` **无限递归**（`util.py:196/206` 往复）。
3. **根因**：pywebview 启动时会递归遍历 `js_api` 对象图来生成 JS 接口（`get_functions`）。桌面的 `DesktopApi` 里存了 `api.window = window` **反向引用**，遍历到 window 后一路进入其内部 .NET 控件代理；这些代理每次 `getattr` 都生成**新代理对象**，`id()` 去重失效 → 无限递归 → 主线程等锁 → 窗口无响应。（深层"为何冻结版才触发"未再深挖，因修复方向已明确。）
4. **修复**（`ccc3081`）：`DesktopApi` 不再持有 window 引用，取窗口一律 `webview.windows[0]`；行为不变。
5. 验证：重建文件夹版，窗口 `Responding=True`、标题正常；用户实机确认可用。
6. 沉淀：把"js_api 严禁反向持有 window"记入 `docs/桌面打包与维护指南.md` 第七节；临时探针/py-spy 已清理。

## 环境与常用操作备忘

- 依赖：`requirements.txt`（运行）与 `requirements-dev.txt`（pytest/pywebview/pyinstaller）；国内网络用阿里镜像 `-i https://mirrors.aliyun.com/pypi/simple/`。
- 桌面重打包：退出 RedNote → `cd frontend && npm run build` → `build_exe.ps1`（默认文件夹版）。
- 数据目录：源码 `data/`，exe `%APPDATA%\RedNote`；`REDNOTE_DATA_DIR` 可覆盖。
